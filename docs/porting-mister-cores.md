# Porting MiSTer Arcade Cores to Game Bub

This document describes how a developer would port a [MiSTer FPGA](https://github.com/MiSTer-devel)
arcade core to the Game Bub platform. It assumes you've read [architecture.md](architecture.md)
and [simulator.md](simulator.md), and that you're comfortable with both SystemVerilog and Chisel.

> **Status:** Game Bub ships only the from-scratch Game Boy / GBA cores today. There is no
> arcade core in the tree. This is a design guide, not a description of existing code — but
> every Game Bub interface it references is real and current.

## 1. The fundamental mismatch

MiSTer cores and Game Bub cores solve the same problem but expect completely different
environments. The porting effort is almost entirely about bridging that gap.

| | **MiSTer core** | **Game Bub core** |
|---|---|---|
| HDL | SystemVerilog | Chisel (Scala), with SystemVerilog glue |
| Framework | The `sys/` folder: `emu` module, `hps_io`, `conf_str`, video mixer/scaler, gamma, OSD | `HandheldTop` (Chisel) + `top.sv` glue; no equivalent framework inside the core |
| Host CPU | Linux on the HPS, talking over a wide memory-mapped bus | ESP32-S3 MCU, talking over a 40 MHz QSPI link |
| ROM delivery | `ioctl_download` streaming bus; ROMs assembled by an MRA file at runtime | MCU streams a pre-assembled blob into FPGA SDRAM / a download window |
| Clocking | A per-core PLL generating several clocks | One `clk_sys` per bitstream, generated by a board-level clock wizard |
| Video | Free-running `RGB + HS/VS/HBlank/VBlank + ce_pix` stream, scaled by `sys` | Pixel-by-pixel writes into a triple-buffered framebuffer |
| Config / DIPs | `conf_str` string parsed into an OSD; `status` bits returned | Config registers written by the MCU; no OSD |
| Target FPGA | Cyclone V (MiSTer) / large Cyclone 10 (MiSTer Multi) | Xilinx Artix-7 `XC7A100T` |

You **do not port the `sys/` folder.** You port the core's `emu` module and its submodules,
and you write a new, much smaller adapter that plays the role `sys/` used to play. That
adapter is the bulk of the work, and on Game Bub it is written in Chisel.

The recommended strategy:

1. Bring the core's SystemVerilog into the `fpga/` build as-is.
2. Wrap the core's top module in a Chisel `BlackBox`.
3. Write a Chisel `HandheldModule` (e.g. `HandheldArcade`) that instantiates that `BlackBox`
   and adapts it to the `HandheldIo` contract — clocks, video, audio, input, ROM loading,
   config.
4. Add a matching bitstream driver to the MCU firmware.

## 2. The `HandheldModule` contract

Every Game Bub core is a Chisel `Module` that mixes in the `HandheldModule` trait and
exposes a `HandheldIo` bundle. `HandheldTop` instantiates exactly one inner module per
bitstream, wires it to the SPI link, framebuffer, audio, RAM arbiters, cartridge pins, etc.
The existing inner modules — `HandheldGameboy`, `HandheldGba`, `HandheldBoot` — are your
reference implementations.

See `fpga/src/main/scala/platform/handheld/HandheldTop.scala` for the definitive interface.

### 2.1 The trait

```scala
trait HandheldModule {
  def io: HandheldIo
  def framebufferW: Int     // core's native framebuffer width  (pixels)
  def framebufferH: Int     // core's native framebuffer height (pixels)
  def clockSystemHz: Int    // the rate clk_sys runs at for this bitstream
  def clockSdramHz: Int     // SDRAM clock; must be an integer multiple of clockSystemHz
}
```

`clockSdramHz` being an integer multiple of `clockSystemHz` is load-bearing — it's what
keeps the SDRAM clock-domain crossing cheap. `HandheldGameboy` uses `clockSystemHz * 4`.

### 2.2 `HandheldIo`

The inner module is clocked by Chisel's implicit clock, which `top.sv` drives with
`clk_sys`. Everything below is in that clock domain unless noted.

- **`enable: Input(Bool)`** — high when the core should run. The MCU gates this via
  `REG_CONTROL`. Typically you AND this into your core's clock-enable.
- **`reset: Input(Bool)`** — active-high core reset, also from `REG_CONTROL`.
- **`buttons: Input(HandheldButtons)`** — 12 active-high buttons (`a b x y up down left
  right l r start select`), already synchronized and de-inverted by `HandheldTop`.
- **Video output** — `framebufferX/Y: UInt(8.W)`, `framebufferData: ColorARGB.rgb555()`,
  `framebufferWriteEnable: Bool`, `vblank: Bool`. You write one pixel per cycle into a
  triple-buffered framebuffer; a rising edge of `vblank` latches the completed frame.
- **Audio output** — `audioLeft/audioRight: Output(SInt(16.W))`. Held values, point-sampled
  in the AV clock domain (see §6).
- **`vibrate: Output(Bool)`** — rumble motor.
- **Cartridge** (`cartridgeEnabled`, `cartridge: HandheldCartridge`) — the physical GB/GBA
  cartridge pins. An arcade core leaves these disabled (`cartridgeEnabled := false.B`, all
  `*Dir := false.B`).
- **`link: HandheldLink`, `pmod: HandheldPmod`** — link port and PMOD header. Stub them
  unless your core uses them.
- **`mcuInterface: MemoryInterface(addressWidth = 30, dataWidth = 32)`** — the MCU's window
  into your core. This is how the firmware reads/writes config registers and streams data.
  You almost always split it with `MemoryMap` / `RegisterMap` (see §8).
- **`sram: Flipped(MemoryInterface(18, 16))`** — 512 KiB of asynchronous SRAM, 16-bit words,
  shared (arbitrated) with the MCU.
- **`sdram: Flipped(MemoryInterface(25, 32))`** — ~32 MiB of SDRAM, 32-bit logical words,
  shared (arbitrated) with the MCU. This runs in the `clk_sys` domain — `HandheldTop` does
  the CDC to the real SDRAM clock for you.

### 2.3 The `MemoryInterface` protocol

`sram`, `sdram`, and `mcuInterface` all use the same simple handshake
(`fpga/src/main/scala/lib/mem/MemoryInterface.scala`):

```
address, write, dataWrite, writeStrobe  -- inputs
dataRead, done                          -- outputs
enable                                  -- raise to start; hold until `done`
```

Raise `enable` with the address/write fields valid, hold them, and wait for `done`. It is
multi-cycle and may stall (the MCU arbiter can interleave its own accesses). `HandheldGba`'s
`DirectReadCache` usage and `HandheldGameboy`'s `emuCart` access state machine are good
patterns to copy for feeding a core that expects single-cycle ROM reads.

## 3. Triage the core before you start

Not every MiSTer arcade core is a good fit. Before writing any code, check:

- **License.** Game Bub's `fpga/` tree is `GPL-3.0-only`. Most MiSTer cores are GPL or
  similar and are compatible, but confirm per-core and preserve attribution and license
  headers. Some cores have non-commercial or "no derivatives" clauses — those cannot be
  merged.
- **Native resolution and orientation.** Game Bub's panel is physically rotated 90°.
  `HandheldTop` integer-scales the framebuffer by **2×** for the internal display
  (480×320 active) and **3×** for HDMI (720×480 active), then centers it. With the fixed 2×
  scale, a core's `framebufferW × framebufferH` must fit within **240×160** to display
  without modification — exactly the GBA's size. Vertical arcade games (e.g. 224×256) and
  anything larger need either a `HandheldTop` change to support a per-module scale factor,
  or in-core downscaling. Plan for this early; it is the most common blocker.
- **Block RAM budget.** The `XC7A100T` has ~4.8 Mbit of block RAM. `HandheldTop` already
  spends three framebuffers (`framebufferW*framebufferH*16` bits each) plus an overlay
  buffer. MiSTer arcade cores that keep large tile/sprite ROMs in block RAM may not fit —
  you may have to relocate those ROMs to SDRAM.
- **Clocking.** List every clock the core's PLL generates and the real frequency of each.
  If the core fundamentally needs multiple asynchronous clocks, see §5.
- **ROM size and layout.** Find the core's MRA file(s). Note the total assembled size and
  whether it exceeds the ~32 MiB SDRAM. Note which `ioctl_index` values the core expects.
- **SDRAM/DDR usage.** Check whether the core uses MiSTer's `sdram`/`ddram` interfaces for
  working memory (not just ROM). If so you'll arbitrate that against ROM access through the
  single `io.sdram` port.

## 4. Bringing the Verilog into the build

The FPGA build is driven by FuseSoC via `fpga/gameboy.core`. Bitstreams are selected by a
`module_*` flag; each flag pulls in filesets, a Chisel `generate` target, and the matching
inner-module class.

### 4.1 Add the core's sources as a fileset

Drop the core's SystemVerilog under `fpga/verilog/arcade/<corename>/` and add a fileset to
`gameboy.core`:

```yaml
  arcade:
    files:
      - verilog/arcade/<corename>/core_top.sv : { file_type: systemVerilogSource }
      - verilog/arcade/<corename>/...         : { file_type: systemVerilogSource }
      # plus any .vh include files with { is_include_file: true }
```

If the core needs its own clock wizard, add a `handheld_clk_arcade` fileset with a
`clk_wiz_system_arcade.v` (copy the structure of `clk_wiz_system_gameboy.v`).

### 4.2 Add the build flag and targets

In `gameboy.core`:

- Add `handheld_clk_arcade` (and `arcade`) to the `_handheld` target's `filesets` list,
  guarded by `module_arcade ? (...)`, mirroring `module_gameboy`/`module_gba`.
- Add a `module_arcade ? (platform.handheld.HandheldArcade)` line to the `handheld`
  generator's `extraargs`.
- Optionally add a `sim_arcade` fileset/generator and wire it into the `sim` target for
  simulator support (see §10).

Build it with:

```sh
fusesoc --cores-root . --work-root=build/arcade --target=handheld_rev2 --flag=module_arcade elipsitz:gameboy:gameboy
```

(The flag name must match what you reference in `gameboy.core`. The existing flags are
`module_boot`, `module_gameboy`, `module_gba`.)

## 5. The Chisel wrapper and clocking

Create `fpga/src/main/scala/platform/handheld/HandheldArcade.scala`:

```scala
class HandheldArcade extends Module with HandheldModule {
  val io = IO(new HandheldIo)
  def framebufferW = 240          // <= 240 for the fixed 2x internal scale
  def framebufferH = 160          // <= 160
  def clockSystemHz = 48 * 1000 * 1000   // pick to suit the core
  def clockSdramHz  = clockSystemHz      // integer-multiple constraint still applies

  // Declare the MiSTer core's top module as a BlackBox.
  class CoreTop extends BlackBox with HasBlackBoxResource {
    val io = IO(new Bundle {
      val clk = Input(Clock())
      val reset = Input(Bool())
      // ... every port of the core's emu module ...
    })
  }
  val core = Module(new CoreTop)
  core.io.clk := clock
  // ... adapters below ...
}
```

The `BlackBox` port bundle must name-match the SystemVerilog module's ports. FuseSoC
already compiles the `.sv` via the `arcade` fileset, so no `addResource` is needed for the
hardware build (it *is* needed for Verilator sim — see §10).

### Clocking strategy

The inner module gets exactly one clock (`clk_sys` at `clockSystemHz`). MiSTer cores
usually expect a PLL handing them several. You have three options, in order of preference:

1. **Clock enables only.** If the core (or a lightly modified version) can run off one fast
   clock with internal clock-enable strobes — the way `HandheldGameboy` drives the GB core
   with `clockConfig.enable` — this is by far the cleanest. Pick `clockSystemHz` at or above
   the core's fastest clock and synthesize the slower domains as enables.
2. **MMCM inside the wrapper.** Instantiate a Xilinx `MMCME2`/`PLLE2` as a `BlackBox` inside
   `HandheldArcade` and derive the extra clocks there. Anything genuinely in another clock
   domain then needs proper CDC (see the `xilinx.XpmCdc*` helpers).
3. **Extend the platform.** Add a clock wizard output in `top.sv`, thread a new
   `Input(Clock())` through `HandheldIo` and `HandheldTop` into the inner module. This is
   the most invasive — only do it if 1 and 2 don't work.

Whatever you choose, gate the core's run-enable with `io.enable` and honor `io.reset`.

## 6. Video adapter

MiSTer cores emit a free-running raster: `VGA_R/G/B`, `VGA_HS/VS`, `VGA_HB/VB` (or
`HBlank/VBlank`), and a `ce_pix` strobe marking valid pixels. Game Bub wants pixel writes
addressed by `(framebufferX, framebufferY)`.

Write a small state machine — `HandheldGameboy` and `HandheldGba` both contain one you can
adapt almost verbatim:

- On `ce_pix` with the core not in blanking and `pixel valid`: set `framebufferWriteEnable`,
  drive `framebufferData` (convert the core's RGB to RGB555 — drop low bits), and increment
  `framebufferX`.
- On a falling edge of `HBlank` (start of a new line): reset `framebufferX := 0`, increment
  `framebufferY`.
- On `VBlank`: reset `framebufferX`/`framebufferY` to 0, and pulse `io.vblank`. The rising
  edge of `io.vblank` is what tells `TripleBufferControl` the frame is done — make sure it
  happens exactly once per frame and only when a full frame has been written.

Resolution and orientation: if the core is larger than 240×160 or is a vertical game, decide
here whether to (a) crop, (b) line/pixel-double-skip to downscale, or (c) modify
`HandheldTop` to accept a per-module integer scale. The display is already physically
rotated, so a vertical core may actually map *naturally* onto the panel — but `HandheldTop`'s
scaling math (`videoScale`, `videoOffsetX/Y`) assumes the GBA/GB aspect, so check it.

## 7. Audio adapter

`io.audioLeft` / `io.audioRight` are `SInt(16.W)` *held values*. `HandheldTop` crosses them
into the AV clock domain with a continuous handshake and feeds the I2S DAC at ~48 kHz, and
the HDMI audio path. Just connect the core's signed 16-bit output:

```scala
io.audioLeft  := core.io.audio_l.asSInt
io.audioRight := core.io.audio_r.asSInt
```

Note this is **point-sampling**, not a real resampler — the AV side simply reads whatever
value is currently presented. For most arcade audio this is acceptable; if the core outputs
a high-rate stream with audible aliasing, add a simple low-pass/decimation filter in the
wrapper. Match the core's output amplitude to roughly fill 16 bits (the GB/GBA modules
shift their APU output left by 6).

## 8. ROM loading and the `ioctl` download interface

This is the second-biggest piece of work after clocking.

MiSTer arcade cores receive their ROM via the `ioctl_download` bus: `ioctl_download`,
`ioctl_wr`, `ioctl_addr`, `ioctl_dout`, `ioctl_index`. The HPS assembles the ROM at runtime
from an **MRA** file (which describes how to interleave/byte-swap MAME ROM parts) and streams
the result. Game Bub has no MRA engine and no HPS.

**Pre-assemble the ROM offline.** Use MAME plus an MRA tool (e.g. `mra`) on a PC to produce
a single flat `.rom` blob — exactly the byte stream the MiSTer core would have received over
`ioctl`. Ship that blob on the SD card. This blob, not a MAME zip, is what the firmware
loads.

**Replay it as `ioctl` writes.** Expose a "download window" in your module's
`mcuInterface` and have the wrapper turn MCU writes into the `ioctl` protocol the core
expects. Structure `mcuInterface` with `MemoryMap` (prefix-matched on the top address bits),
exactly like `HandheldGameboy` does:

```scala
io.mcuInterface <> MemoryMap(addressWidth = 24, dataWidth = 32, entries = Seq(
  "b0000".U(4.W) -> registerInterface,   // config registers (RegisterMap)
  "b0001".U(4.W) -> downloadInterface,   // ioctl replay window
))
```

The `downloadInterface` state machine takes each 32-bit MCU write and drives `ioctl_wr` /
`ioctl_addr` / `ioctl_dout` (and a fixed or register-selected `ioctl_index`) into the core,
holding `ioctl_download` high for the duration. The MCU writes the `.rom` blob sequentially
while the core is held in reset.

For very large ROMs, the alternative is to stream the blob into **SDRAM** with the
firmware's `sdram_write` and have the wrapper service the core's ROM reads from `io.sdram`
— but only if the core reads ROM from an SDRAM-like interface rather than expecting
everything pre-loaded into block RAM. Many arcade cores expect the latter, which is why the
`ioctl` replay window is usually the right call.

**NVRAM / high-score saves.** If the core has battery-backed RAM, route it to `io.sram` and
reuse the firmware's existing save-persist mechanism (`persist_save` reads SRAM back to a
`.sav` file). `HandheldGba`'s EWRAM-vs-emucart SRAM arbiter shows how to share the 512 KiB.

## 9. DIP switches, config, and reset

There is no OSD and no `conf_str`. Anything the user would toggle in the MiSTer OSD —
DIP switches, region, freeplay, the `status` bits the core reads — becomes a **config
register** in your `RegisterMap`, written by the MCU firmware.

```scala
val configRegDips = RegInit(0.U.asTypeOf(new Bundle { /* ... */ }))
registerInterface <> RegisterMap(addressWidth = 16, dataWidth = 32, entries = Seq(
  0x0000 -> RegisterMap.Entry.rw(configRegDips),
  // stats / status registers as needed
))
```

`RegisterMap` gives combinational reads and single-cycle writes (see
`fpga/src/main/scala/lib/mem/RegisterMap.scala`). Map the core's `status`/DIP inputs from
these registers. Wire `io.reset` (and the MCU's `enable`) into the core's reset/enable.
Input mapping (`HandheldButtons` → the core's `joystick_0` bitfield, coin/start lines) also
lives in the wrapper — pick a sensible fixed mapping; Coin is commonly Select, Start is
Start.

## 10. Simulator support (optional but recommended)

The Verilator simulator (`docs/simulator.md`) is the fastest debug loop. To get an arcade
core into it:

- Add a `platform.sim.SimArcade` top-level mirroring `SimGameboy`/`SimGba`, exposing
  `PpuOutput`-style video, audio, and input plus a way to preload the ROM blob.
- Add `sim_arcade` filesets and a `sim_arcade` generator to `gameboy.core`, and a
  `module_arcade ? (sim_arcade)` entry to the `sim` target.
- Add C++ glue under `fpga/sim/arcade/` (cartridge/ROM loading, controls) following
  `fpga/sim/gb/` and `fpga/sim/gba/`.
- For Verilator, the `BlackBox` needs the `.sv` available — either rely on the `arcade`
  fileset being included in the `sim` target, or use `HasBlackBoxResource`/`addResource`.

Build/run:

```sh
fusesoc --cores-root . run --target=sim --flag=module_arcade elipsitz:gameboy:gameboy
./build/.../sim-verilator/VSimArcade --rom <assembled.rom>
```

## 11. Firmware: the bitstream driver

The MCU side mirrors the FPGA side. Each core type has a *bitstream driver* under
`firmware/handheld/src/bitstream/`. See `gameboy.rs` and `gba/` for full examples.

### 11.1 The driver

Create `firmware/handheld/src/bitstream/arcade.rs` with a struct implementing the
`Bitstream` trait (`firmware/handheld/src/bitstream/mod.rs`):

```rust
pub trait Bitstream {
    fn get_bitstream_path(&self) -> &'static str;   // e.g. "arcade.bit.gz"
    fn on_after_program(&mut self) -> Result<(), String>;
    fn set_paused(&mut self, paused: bool) -> Result<(), fpga::Error>;
    fn reset(&mut self) -> Result<(), fpga::Error>;
    fn on_vblank_irq(&mut self);
}
```

`on_after_program` should call `fpga.set_system_clock_rate(...)` with this core's
`clockSystemHz` (the firmware uses it to pick a safe QSPI clock). Then add inherent methods
for the ROM/save lifecycle — mirror `Gameboy::set_emulated_cartridge` /
`persist_ram` / `needs_save_persist`.

In `set_emulated_cartridge`:

1. Hold the core in reset: `write_u32(REG_CONTROL, 0b0000)`.
2. Stream the assembled `.rom` blob into the download window (the `mcuInterface` region the
   MCU sees at the `0xC0_xx_xx_xx` module space) — or into SDRAM via `fpga.sdram_write` if
   that's your design — in chunks, sending `ui::Message::RomLoadingProgress`.
3. Write config registers (DIP defaults, etc.).
4. Optionally load NVRAM into SRAM via `fpga.sram_write`.
5. Release: `write_u32(REG_CONTROL, 0b1011)` (reset released, running).

### 11.2 Wire it into the firmware

The trait is intentionally minimal; the worker and game-state code match on the
`CurrentBitstream` enum directly, so adding a core means touching several `match` arms:

- **`firmware/handheld/src/bitstream/mod.rs`** — add an `Arcade(arcade::Arcade)` variant to
  `CurrentBitstream`, update `get()`, and add an `ensure_arcade()` constructor.
- **`firmware/handheld/src/worker/mod.rs`** — add the file extension(s) (e.g. `"zip"` or a
  custom `".gbub"`) to the `rom_select_get_files` filter list **and** the `RunRomFile`
  dispatch `match`; add arms in `RunCartridge`/`SaveGame` as needed.
- **`firmware/handheld/src/ui/state/game.rs`** — add arms in `on_game_set_paused` and
  `on_game_reset`.
- The Slint UI is generic — no `.slint` changes are needed unless you add core-specific
  settings screens. If you do add settings (DIP toggles, region), add KVS keys in
  `firmware/handheld/src/kvs/keys.rs` and entries under `src/ui/state/settings.rs` +
  `res/ui/screens/settings/`.

> A worthwhile refactor while you're here: lift `set_emulated_cartridge` / `persist_save` /
> `needs_save_persist` into the `Bitstream` trait so these `match` blocks collapse to trait
> calls. Currently they're duplicated per variant.

### 11.3 SD card layout

The firmware resolves system files from `/sdcard/system_rev{1,2}/` then `/sdcard/system/`.
Place your bitstream and any assembled ROMs accordingly:

```
system/
  arcade.bit.gz        # gzip'd copy of the module_arcade bitstream
roms/
  <game>.rom           # offline-assembled ROM blob (the ioctl byte stream)
```

`partitions.csv`, `flash_nvs.py`, and `sdkconfig.defaults` do **not** need changes for a new
core — bitstreams and ROMs live on the SD card, not in ESP32 flash.

## 12. Build, flash, test

```sh
# FPGA bitstream
cd fpga
fusesoc --cores-root . --work-root=build/arcade --target=handheld_rev2 --flag=module_arcade elipsitz:gameboy:gameboy
gzip -c build/arcade/.../top_handheld.bit > arcade.bit.gz   # copy to SD: system/arcade.bit.gz

# MCU firmware
cd ../firmware/handheld
cargo run --release --features=rev2
```

Iterate in the Verilator simulator first (§10) — rebuilding a bitstream is slow.

## 13. Known constraints and gotchas

- **Fixed 2× display scale.** Until `HandheldTop` learns a per-module scale factor, the
  effective max framebuffer for the internal display is 240×160. This is the single most
  common reason a core won't "just work."
- **One core clock.** Multi-clock-domain cores need real CDC or a clock-enable rewrite.
  Don't paper over async crossings.
- **Block RAM is shared.** Three framebuffers + overlay are already spent. Large in-core
  ROMs may have to move to SDRAM.
- **SDRAM is one arbitrated port.** ROM reads, core working memory, and MCU access all share
  `io.sdram`. Budget the bandwidth; the SDRAM runs in the `clk_sys` domain at
  `clockSdramHz`, an integer multiple of `clockSystemHz`.
- **Audio is point-sampled**, not resampled. Filter in the wrapper if it aliases audibly.
- **No OSD / `conf_str`.** Every user-facing option becomes a config register plus firmware
  + (optionally) Slint settings UI.
- **No MRA at runtime.** ROMs must be assembled offline into the flat `ioctl` byte stream.
- **Licensing.** Per-core check; `fpga/` is `GPL-3.0-only`. Preserve attribution.
